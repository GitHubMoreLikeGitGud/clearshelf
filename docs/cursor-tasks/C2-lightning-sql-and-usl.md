# C2: Lightning SQL review and static tests

## Goal

A static test suite, `gateway/tests/test_sql_scripts.py`, checks every Lightning SQL pair in `zetaris/sql/` and `zetaris/manifest.json`. The statements are also reviewed against the saved source samples, and the findings are reported.

The SQL, the manifest and `zetaris/README.md` are not part of this task. Pairs 00 to 13 were written and run against the local instance during the Day-0 gates, and their results (row counts, DQ results, measured behaviour) are recorded in `zetaris/README.md`. Cursor Agent reviews them and reports findings; it does not write or rewrite them.

## Workspace

This repository. Pass the getting-started clone as a read-only extra root for its SQL guides: `--add-dir <path to the getting-started clone>`.

## Read first

- `AGENTS.md`, `.cursor/rules/zetaris.mdc`, `.cursor/rules/data-licences.mdc`.
- `zetaris/README.md` (the Day-0 gate results) and `zetaris/manifest.json`. If either is missing, stop and report; do not start the task.
- Every file in `zetaris/sql/` (the pairs below).
- `gateway/jdbc.py` (`split_statements`), `gateway/allowlist.py` (`check`, roles `reader` and `onboard`), `gateway/run_sql.py` (`--dry-run`), `gateway/sqlgen.py` (which statements it generates), and the existing tests in `gateway/tests/`, in particular `test_allowlist.py`, which already checks every statement in `zetaris/sql/` against the `onboard` role.
- In the getting-started clone: `AGENTS.md` ("Writing SQL"), `docs/guides/zetaris-lightning-sql-companion.md` (sections 2, 4, 5 and 8) and `docs/guides/zetaris-lightning-sql-commands.md` (sections 6, 13, 14 and 19).

### The pairs in `zetaris/sql/`

| Pair | Contents |
|---|---|
| `00_clearshelf_base_*` | The four `CLEARSHELF_*` Lightning databases, the `clearshelf` SchemaStore container, the namespaces `lightning.metastore` and `lightning.metastore.clearshelf`. |
| `01_fda_enforcement_*` | REST table `clearshelf_fda.enforcement_undeclared` (openFDA, `{meta, results[]}`), then `CACHE TABLE`. |
| `02_fsa_allergy_alerts_*` | REST table `clearshelf_fsa.allergy_alerts` (FSA, `{meta, items[]}`, double explode through `problem[].allergen[]`), then `CACHE TABLE`. |
| `03_ops_*` | REST tables `health`, `market_allergens`, `decisions`, `recall_links`, `extractions` `FROM CLEARSHELF_OPS` on `http://clearshelf-ops/<name>.json`, not cached. |
| `04_off_products_*` | One Open Food Facts REST table per gate SKU (three), each with `CREATE`, `DESCRIBE` and `CACHE`. The full SKU set is generated by `gateway/sqlgen.py` from the intake manifest. |
| `10_clearance_usl_*` | `COMPILE USL IF NOT EXISTS clearance_usl ...` (one statement, nine `CREATE TABLE`), then `UPDATE USL ... DESCRIPTION` for the USL, every table and the key columns. |
| `11_clearance_usl_activate_*` | `ACTIVATE USL TABLE` for all nine tables. The `product` and `declared_allergen` statements are marked `GENERATED by gateway/sqlgen.py`. |
| `12_clearance_dq_*` | `REGISTER DQ` for `has_ingredients`, `english_label`, `known_relation`; the select file has `LIST DQ`, `RUN DQ`, `SHOW DQ INVALID RECORD` and the DQ-equivalent plain SQL. |
| `13_reactivate_probe_*` | Gate G6 probe: re-activates `product` with a changed query. Generated by `gateway/sqlgen.py`. |

## Inputs

Saved source responses. They are gitignored, never committed and never quoted into committed files. Use them only to confirm field names and nesting. Do not call the source APIs and do not connect to Zetaris.

- `data/curation/raw/fda_enforcement_undeclared.json`: openFDA, `{meta, results[]}`, 1,000 results.
- `data/curation/raw/fsa_allergy_alerts.json`: FSA, `{meta, items[]}` with `problem[].allergen[]`, 200 items.
- `data/curation/off/<gtin13>.json`: one file per Open Food Facts lookup made during curation. Each file is a wrapper `{gtin, why, url, fetched_at, http_status, error, body}`; the API response is under `body` (`body.code`, `body.status`, `body.status_verbose`, `body.product`). Product fields are under `body.product.*` (`code, product_name, brands, lang, ingredients_text, ingredients_text_en, allergens_tags, traces_tags, labels_tags, countries_tags, last_modified_t`). Optional fields can be absent: for example `0816929000119` has no `brands` and no `ingredients_text`, and `4056489125846` has no `ingredients_text_en`. Files with `http_status` 404 have `body.status` 0 and no `body.product`; skip them.

The Zetaris REST table for an OFF product has the same nesting as `body`: top-level `code`, `status`, and a `product` struct.

## Deliverables

| File | Contents |
|---|---|
| `gateway/tests/test_sql_scripts.py` (new) | Static checks over every file in `zetaris/sql/` and over `zetaris/manifest.json` (see Checks). Standard library and pytest only. Do not repeat the `onboard` allowlist check that `test_allowlist.py` already makes. |

Review findings are not written into any file. List them in the final message (file, statement number from the dry-run output, the problem, the proposed text); they are recorded in this file's run record.

### Review checklist (read-only)

1. Every source field an activation in `11_` reads exists in the saved samples, at that nesting: openFDA `results[]` (`recall_number, report_date, classification, status, recalling_firm, distribution_pattern, product_description, reason_for_recall, code_info`), FSA `items[]` (`notation, created, title, reportingBusiness.commonName, alertURL, problem[].allergen[].label`), OFF `product.*`.
2. Every `NOT NULL` column in the `10_` DDL is, in every activation and every `UNION ALL` branch, either `COALESCE(...) AS <column>` or a quoted literal `AS <column>`.
3. Every ops activation (`market_allergen`, `extracted_allergen`, `recall_product_link`, `decision`) uses `LATERAL VIEW explode(data) x AS d` and filters `d.<pk> <> '__schema__'`.
4. The three `REGISTER DQ` expressions in `12_` match the build plan exactly:
   - `has_ingredients` on `product`: `ingredients_text IS NOT NULL AND length(trim(ingredients_text)) > 0`
   - `english_label` on `product`: `lang = 'en' OR (ingredients_text_en IS NOT NULL AND length(trim(ingredients_text_en)) > 0)`
   - `known_relation` on `extracted_allergen`: `relation IN ('contains','may_contain','free_from_claim','not_allergen')`
5. The expected counts in the `_select.sql` comments agree with the counts recorded in `zetaris/README.md`.
6. Nothing selects `address_1`, `address_2`, `postal_code` or an Open Food Facts contributor field (`creator`, `last_editor`, `editors_tags`, `informers_tags`, `correctors_tags`, `photographers_tags`, `checkers_tags`).
7. Each manifest entry's `requires` covers every object its script reads (for example, `11_` reads the tables that 01 to 04 create), and each `status` agrees with `zetaris/README.md`.

## Constraints

- **Never edit any file in `zetaris/`** (the SQL, `manifest.json`, `README.md`), not even comments. Those files record what ran against the instance at the Day-0 gates. If something looks wrong, report it; the owner of the SQL decides.
- Never hand-edit generated statements (the `GENERATED` blocks in `11_`, the SKU blocks in `04_`, all of `13_`), never edit `gateway/*.py`, and never edit the existing tests. If a check exposes a gap in the allowlist or the splitter, report it; do not loosen the allowlist, the splitter or the test.
- Do not connect to Zetaris and do not call any source API. `run_sql --dry-run` is the only runner use.
- No credentials, no contact e-mail, no Open Food Facts ingredient text in any committed file, including test fixtures.

## Checks

- `.venv/Scripts/python -m pytest gateway/tests/test_sql_scripts.py` is green. The test asserts:
  - every file in `zetaris/sql/` is named `NN_<name>_create.sql` or `NN_<name>_select.sql` and has its partner;
  - every `_create.sql` is the `script` of exactly one entry in `zetaris/manifest.json`, every `script` path exists, ids are unique, every `requires` id exists, the dependency graph has no cycle, and the `00_` entry is the only one with no requirements;
  - every statement of a `_select.sql` (split with `gateway.jdbc.split_statements`) passes `gateway.allowlist.check(s, "reader")`;
  - no statement ends with `;`;
  - `10_clearance_usl_create.sql` yields exactly one `COMPILE USL` statement containing nine `CREATE TABLE`, with the table names, primary keys and foreign keys in the keys table above;
  - every `DESCRIBE BY` text matches `^[A-Za-z0-9 _.,-]+$`;
  - every `user-agent` header value is exactly `YOUR_APP_NAME YOUR_CONTACT_EMAIL`, and no SQL file contains `@`;
  - no statement (after splitting, so comments are excluded) contains a forbidden column (checklist item 6) or any of the words `DROP`, `GRANT`, `REVOKE`, `INVALIDATE CACHE` or `8889`;
  - every qualified object name after `FROM`, `JOIN` or `TABLE` starts with `clearshelf_` or `lightning.metastore.clearshelf`, and every REST table is created `FROM CLEARSHELF_*`;
  - checklist items 2 and 3 hold for `11_clearance_usl_activate_create.sql`, and it activates all nine tables.
- `.venv/Scripts/python -m pytest gateway/tests` is still green (live tests stay skipped unless `CLEARSHELF_LIVE=1`).
- `.venv/Scripts/python -m gateway.run_sql <file> --dry-run` exits 0 for every file in `zetaris/sql/`.
- `cd agent && npm test` still passes (no agent changes expected).
- `git status` shows only the new test file.
